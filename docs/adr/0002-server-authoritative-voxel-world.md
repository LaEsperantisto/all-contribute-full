
## Amendment — menu-first boot, presence, namespaces, day/night, cascade delete (2026-11-07)

**Boot is the main menu; the game view is lazy and stays live.** `Join global server` imports the DVE bundle, fetches registry + edits, and creates the view; the player's last pose is restored from `player_state` (persisted every 2 s while moving). `Main menu` from the pause dialog hides the game but keeps the engine and socket alive — rejoining skips re-init and just re-grabs the cursor. Cursor hand-off is explicit (HUD "Grab cursor" button; any closed dialog that leaves no dialog open re-grabs).

**Player blocks are `player:USERNAME:NAMESPACE:BLOCKNAME`** (four segments, exactly like `builtin:` ids); the display name is the separate `name` column. `POST /api/blocks` takes a `namespace` (optional, default `default` for old cached clients); migration 0007 rewrote existing 3-segment ids. **`DELETE /api/blocks/:id` cascades**: placed copies are removed from `world_edits` (terrain restored, broadcast as `air` over the WS), referencing recipes are dropped, inventory stacks are purged — deleting one's test block never requires manual world cleanup.

**Presence rides the existing `/api/world/live` WorldLive object:** clients post a `pose` frame (~4 Hz) with their username; the object keeps a socket→pose map and fans `pose`/`leave` out to the other sockets (a `who` frame pulls the roster). Avatars (blocky body + name card, lerped) are rendered client-side from these frames — presentation only, still no server physics, and a hidden tab's rAF halt freezes its render loop (avatars hold position until the tab is visible).

**Day/night is a deterministic epoch clock** — `Date.now() % 24 min` drives sky colour and an image-processing brightness scale; no sync traffic. **Glowing blocks** (registry `light > 0`) render through a Babylon GlowLayer emissive cube on the cell, not the vlox light pipeline (which stays off; faces would multiply by empty light data). **Generator workers keep every server edit including `air`** and receive live `note-edit` relays, so blocks mined before joining — or in cells that activate late — never render solid.

## Amendment — occlusion fix, saved appearance, recipe ownership, admin grant tool (2026-11-07)

**One rendering group for everything.** vlox renders its voxel sections in Babylon rendering group 1 and Babylon clears the depth buffer between groups, so any mesh left in group 0 (the avatars and glow cubes were) is painted over by voxels that sit *behind* it — the reported "players are only visible when nothing is behind them". Every mesh this app creates now joins `VOXEL_GROUP = 1` in `frontend/dve/src/main.js`. This is an invariant for future meshes, not a tuning knob.

**Character appearance is stored and rides presence.** `player_appearance` (migration 0008, widened by 0011) keeps one `#rrggbb` colour per user (`body_colour`/`head_colour`/`accent_colour`/`eye_colour`), written by `POST /api/player/appearance` and returned by `GET /api/player/state`. Every `pose` frame carries it; the WorldLive object sanitizes it to exactly those four keys before storing/relaying, so presence stays presentation-only. The in-game **C** dialog shows the signed-in username and the four colours; **I** opens the inventory. The look is account data, so it has to arrive with the account: Join starts the world and reads `GET /api/player/state` before you have necessarily signed in, and that first read answers with the defaults; signing in afterwards re-reads the account and repaints your own body, exactly as signing in refreshes the bag, the recipes and the Studio lists. A body built by a signed-out join that is never repainted is the plain default colours in third person while every *other* player sees the saved ones — the presence frames carry the look from the moment the app has it, so the bug is only ever visible to its owner.

**Recipes are owner-managed like blocks.** `GET /api/recipes` returns `creator`; `PUT /api/recipes/:id` and `DELETE /api/recipes/:id` are creator-only and reuse the POST validator verbatim (`recipeFieldsFromInput`), so an edit cannot smuggle fields a create would reject.

**Test-item grants are admin-only in the UI.** The "Add test items" form in the inventory dialog is hidden unless the signed-in username is `admin` (the handler refuses too). Server-side the endpoint is still per-account; real economies come later.

**Escape opens the pause menu in one press.** While pointer-locked Chrome consumes Escape itself (it exits the lock and delivers no keydown), so `openPause()` is driven from the `pointerlockchange` handler — gated on "game visible and no dialog open" so closing a menu never re-opens the pause menu.

## Amendment — items with programmes, sky bodies, mob simulation, health (2026-11-07)

**Items are what a player holds; blocks are what occupies a voxel.** Migration 0009 adds `items`: a `kind` (`block`/`tool`/`weapon`/`food`/`material`), declared stats (`damage`/`speed`/`heal`/`durability`), and `place_block_id` — a placeable item's *programme*, the single block it drops. Creators author an item the same way they author a block (`player:` namespace, creator-only `PUT`/`DELETE`, built-ins immutable). Like block behaviour, the programme is declarative data, never code (ADR 0001 staging). The two registries stay separate on purpose: `blocks` remains the voxel identity used by `world_edits`, `world_log`, textures, and placement rules — the item layer only decides *which* block a held thing writes. So `POST /api/world/place` validates the item (a `kind='block'` item with a programme, else `code:"not_placeable"`), runs the placement rules against the **block** row, debits the **item** stack, and stores the **block** id; `POST /api/world/break` credits the item whose programme is that block (built-in preferred). Deleting an item cascades its inventory stacks and referencing recipes.

**Sky bodies live in rendering group 0 on purpose** — the deliberate inverse of the avatar/glow/mob `VOXEL_GROUP` rule. The sun and moon are unparented emissive billboards on an infinite-distance root that orbits a 0.41 rad tilted axis from the same 24-minute epoch clock as the sky colour; because Babylon clears depth between render groups, group 0 draws *behind* every voxel, which is exactly what a sky body needs. Distance is derived from `camera.maxZ` so render-distance changes never clip them.

**Presence carries velocity and receivers dead-reckon.** `pose` frames now include `vx,vy,vz` (blocks/sec, clamped server-side to ±30). Receivers coast the avatar along that velocity for at most 0.6 s between frames, ground-clamp the extrapolation with the local terrain mirror when near the local player, and refuse an extrapolation that would engulf the camera — so 5 Hz presence reads as continuous motion, and a frozen sender pins in place rather than running away.

**Mobs are simulated inside the `WorldLive` object, ticked by alarms.** Durable Objects have no timers, so the loop is `ctx.storage.setAlarm(Date.now()+250)` re-armed at the end of each `alarm()` while at least one socket is connected (and never armed when the room is empty). The object keeps at most 12 mobs on the terrain surface, and they arrive on their own: each tick adds one at a **40-50 block ring** around a randomly chosen live player (never beside them, never on request), and the same tick forgets any mob more than **96 blocks** from every connected player — without that sweep a mob that wandered out of sight held its slot against the cap forever and the world quietly stopped spawning, which is what "mobs never spawn" actually was. Hostiles (`zombie`) steer toward the closest living player within a **56-block sphere** — deliberately just past the ring, so a mob born at its far side still notices the player it was born for — and hit once per ~1.2 s when the **3D** gap closes to 1.8 blocks — every range test uses `hypot(dx,dy,dz)`, so a player standing above a mob is out of reach even when their columns coincide, while the mob's *steering* stays horizontal because it walks the surface; peaceful mobs (`pig`) wander on a 3–6 s heading timer. Clients receive **full snapshots** (`{type:"mobs",mobs:[…]}`, ~4 Hz) rather than deltas, so one dropped frame self-heals, and only lerp toward them — no client-side mob physics exists.

**Health is owned by the server, and the single source of truth is kept across the REST/DO boundary.** `player_state.health` (migration 0010) is written by the object when a mob lands a hit and by `POST /api/player/respawn` / `POST /api/player/eat`. Those REST handlers write D1 *and* notify the running object through an internal `fetch` on the same DO id, which pushes a `respawn`/`health` frame to that player's sockets — otherwise the object's cached presence health would overwrite the REST write. Death marks the presence entry `dead`: hostiles stop chasing and stop damaging, and the client's hearts/death screen are pure projections of these frames.

**Attacks are claimed by the client but bounded by the object.** A client sends `{type:"attack",mob_id,item_id}`; the object rejects anything that is not a `weapon`/`tool` item, takes the damage from the `items` row (never from the client), and requires the player to be within 6 blocks of the mob. Killing credits a drop to the killer's inventory. This is the same trust posture as the rest of the prototype (movement stays client-side): the object validates *kind, stat, and distance*, not the swing.

## Amendment — fists and PvP, scripted blocks, beams, one Look setting, arranged inventory (2026-11-07)

**An unarmed swing is still a swing.** `handleAttack` no longer requires a weapon: no item (or one that is not `weapon`/`tool`) attacks with `FIST_DAMAGE = 1` at `FIST_RANGE = 3.5`, armed swings keep the item's declared `damage` at 6 blocks, and the per-attacker `ATTACK_COOLDOWN_MS = 600` is a map inside the object, so no client can swing faster than the object allows. The same frame now carries `target` (another player's username) as well as `mob_id`; the victim is chosen from the object's own presence map and re-checked against the 3D distance. So *who* swung and *at what* is client-claimed, while *damage, rate and reach* stay object-owned — the posture is unchanged, only the surface widened to PvP. Being hit is broadcast as `{type:"hit",what:"mob"|"player",id}` and every client renders the white flash, so the feedback no longer depends on the victim's own tab.

**A block can be programmed, in Lua, on the server.** `blocks.script` (migration 0012) holds sandboxed Lua (`backend/src/lua.ts`): no `os`/`io`/`require`/network, a 20 000-instruction and 50 ms budget, and its only inputs are the arguments — `{player}` for `on_interact(player)`, `{player,key}` for `on_choice(key,player)`. The entry contract takes **named argument objects**, and a menu can be returned as a table (`{title,options}`) or built with `menu()` — `readMenuOptions` parses both, and options accept `{red="Red"}`, `{ {"red","Red"} }`, or `{ {key="red",label="Red"} }` so an author's typo degrades to a key rather than a broken dialog. `runBlockScript` never throws: an author's bug becomes `{ok:false,reason:"script-error"}` plus a plain toast, never a 500 or a dead block. **Script memory belongs to the cell** (`block_state`, keyed `x,y,z,key`), not to the player or the block, so two beacons in one world keep independent settings.

**Light columns are state, not effects.** A script calls `beams({colour})`; the Worker rewrites `block_beams` for that cell in the same D1 batch as the state writes, then fans out `{type:"beam",x,y,z,colour|null}` — `colour:null` removes it. `GET /api/world` returns the active `beams` so a player who joins later sees columns that were switched on before they arrived, and `handleBreak` deletes the cell's `block_state`/`block_beams` rows and broadcasts the removal: **destroying the block destroys its program's memory.** The built-in beacon is authored in Lua (migration 0013) rather than hard-coded, so the shipped feature exercises the same path a player-authored script takes.

**One setting decides both block detail and item art.** `render` is a single client setting, `flat` (default) or `detailed`, because block textures and item icons must agree — a bag full of icons next to flat-coloured blocks is neither mode. The Worker ships `texture`/`model`/`icon` payloads as validated data (`sanitizeImage` requires a `data:image/png;base64,…` literal under 60 kB for a block texture, 40 kB for an icon; `sanitizeModel` accepts only ids from the exported `BLOCK_MODELS` list, which `GET /api/blocks` publishes as `models`). The renderer's rule is one expression per block (`frontend/dve/src/main.js`): `useTexture = render==="detailed" && isTexture(b.texture)`, else a generated solid-colour texture; `model = render==="detailed" && MODEL_IDS.has(b.model) ? b.model : "dve_simple_cube"`. Every custom mesh still has to set `renderingGroupId = VOXEL_GROUP`, or terrain paints over it.

**The bag and the hotbar are one list.** The client keeps no separate hotbar array: the `inventory` object's key order *is* the arrangement, the hotbar is its first ten entries (keys **1–9**, then **0**), and the client no longer sorts. Dropping one stack on another **swaps** them — swap rather than insert because one rule has to serve both a wrapping grid and a fixed ten-slot strip, and swapping never changes what is in the hotbar. The order is per account (`inventories.ord`, migration 0014) written by `POST /api/inventory/order` as a single `CASE` update (one statement, so no D1 batch limits and no partial ordering), and `GET /api/inventory` orders `(ord IS NULL), ord, item_id` — NULL sorts last, which is exactly the old alphabetical behaviour, so no backfill. **Arranging is not admin-gated** (it is the player's own bag) while granting/removing counts (`/api/inventory/add|remove|clear`) now 403 for every username but `admin`: the previous admin-only rule was UI-only, and a hidden button is not a permission.

**A remote avatar is a `TransformNode` head on a `Mesh` root.** Live verification caught `ensureRemote` calling `new TransformNode(...)` without the import: every pose frame threw, so `remotes` never filled (no other player was ever visible or attackable) and each attempt leaked a partial root at the origin. The engine now imports `TransformNode` from `@babylonjs/core`.

**A voxel name the terrain never generates still has to encode, and every thread has to agree on the number it encodes to.** Live verification placed the beacon with a real right-click: the server row, the broadcast and the item debit all happened, and the client's world held air - silently. Digging the cell back out with the game's own break is what separated the two engine defects behind that: the dig named the block the player had placed, while the pixels showed terrain through it. (1) *Encode.* vlox's `sync-data` hands each worker the imported palette but assigns the positional tables (`voxelIdToTrueId`, `modelsIndex`, `totalStates`, `voxelRecordStartIndex`, `VoxelTags`) verbatim, so a published block's entry has no record slot: it decodes to composite id 0 - air - and `Brush._paint` writes air without throwing. (2) *Numbering.* Repairing that by allocating a fresh composite id per thread is worse than the defect: ids are positional and threads start from different palette offsets, so the world thread wrote one number and the mesher read another. The mesher then aborts the entire section build - `VoxelTags[...].dve_is_transparent` on undefined, then `modelsIndex[composite]` undefined in `hashState`, which indexes by composite id - and the section never reaches the renderer: the placed block is invisible and a dug hole never closes.
`frontend/dve/src/lut-repair.js` therefore allocates nothing. Run in main, world, generator and mesher the moment the payload lands and on a 2 s interval, it aligns each imported composite with this thread's palette slot, duplicates that entry's trueId-keyed encoding onto the composite index, mirrors whatever the payload left out from a same-name entry, and rebuilds missing `VoxelTags`. The invariant: a palette entry is usable only when its record slot holds a composite id that decodes back to its own palette name. Repairing in one thread is not enough - a raw voxel carries only the number, so the threads that share a byte stream must share the numbering.
**An edit has to re-mesh, not merely be written.** vlox rebuilds a section only when its `displayDirty` tick changes (`SimulationSector.tickUpdate`); a brush write bumps nothing, so a painted cell stayed invisible until the sector unloaded and came back - the live symptom was a placement the player could dig again without ever having seen. `paint-direct` bumps the touched section and its boundary neighbours (the neighbour section owns the shared culled face), retrying briefly for sectors checked out for mesher transfer. The bump target matters: `WorldRegister` has only `sectors` (world coords → `Sector`), and the tick lives on the `Section` inside it (`Sector.getSection` takes world coords), while `Sector` itself has no `incrementTick` — a bump aimed at a `WorldRegister.sections` map that does not exist threw on every edit, was caught as a detached-buffer race, and left blocks on screen until a page reload. The bump is only counted as done when the tick value actually moved, since writes into a detached `tickArray` are silent no-ops.

**The world log is now a bounded queue, not an archive.** It exists so a client that missed a live frame can catch up, and the sparse overlay it feeds is re-fetched whole whenever the socket is down, so history older than that window is worth nothing. Each logged edit therefore prunes the table to the newest 100 rows, and `GET /api/world` returns at most that many entries after the caller's cursor. A cursor older than the retained window is not a failure: the window fetch re-syncs the overlay, which is what correctness actually rests on.

## Amendment — derived rows are derived, and the admin can re-run the truth (2026-11-08)

**`world_edits` is the whole truth about the world; everything else about a voxel is derived.** `world_log` (catch-up), `block_state` (script memory), `block_beams` (light columns) and `block_inventory` (voxel stores) describe a voxel the edit table already agrees on. A derived row whose cell has no `world_edits` row is therefore stale *by construction*, and a stale row must never paint anything. Three places enforce that: the catch-up read (`GET /api/world`) replays a `world_log` entry only when the edit table still holds that cell as that block; `DELETE /api/blocks/:id` prunes the rows its cascade orphaned; and `pruneOrphanWorldRows` is the sweep both the cascade and the resync call. This is the fix for one reported symptom — the server painting a block or a column of light the database says isn't there — which came from a Studio block deletion that cleared `world_edits` but left its log rows behind.

**The repair is to re-run the edit table, and the client has to be told to forget.** Pruning and replaying cannot fix a browser that painted a block the database never had: D1 has nothing to say about a cell it never edited, so no frame can remove it. So `POST /api/world/resync` (admin account only, same exact-username gate as the inventory-surgery tools) prunes the derived rows, replays every surviving edit and light column through the Durable Object as ordinary `edit`/`beam` frames (chunked, ≤20 000 cells), and broadcasts exactly one `resync` frame. Every client that sees it rebuilds its world from the snapshot it re-reads, so the repair reaches everyone connected, not just the admin who pressed the button in the pause menu.

**A phantom voxel is repainted with base terrain, not with air.** The truth about a cell the database never edited is whatever the deterministic generator makes there; writing `air` would dig a hole the world never had. The rebuild diffs the old edit map against the snapshot and calls `applyEdit(x,y,z,dveMod.baseBlock(x,y,z))` for every cell that disappeared. Because `applyEdit` also notes into the generator's edit mirror, that mirror is reloaded wholesale from the API afterwards (the `reload-edits` generator task) — a fake note baked into a generator chunk would otherwise survive the repair and re-mesh.

**A menu is aimed with a cursor, not with the crosshair.** Opening a scripted block's E-menu releases pointer lock before `showModal()`; the existing "any closed dialog that leaves no dialog open re-grabs" rule then hands the cursor back to the game on close. The cursor hand-off invariant (ADR 0002, menu-first boot) now covers block menus as well as the pause menu and the HUD button.

**Clearing a light column asks the renderer, not the caller's list.** Live verification forged a column that existed only as a mesh in one client. The rebuild that removes unlisted columns iterated the client's own last-read `worldBeams` copy — so exactly the column that was stuck, the one whose removal frame never arrived and which therefore never entered that copy, survived the repair. The view now exposes `beamCells()` and the repair asks the engine what it is drawing. The invariant: what is on screen is owned by the renderer; a repair that consults a copy of it can only clear what it already knew about.

**A script may now change the world, not just report on it, and the acting player is its only handle.** `runBlockScript` records a run's effects — beams, toasts, logs, `moves`, `gives`/`takes`, and the cell's final store — and the caller applies them in one D1 batch; the interpreter is synchronous and holds no DB handle, so a run that fails partway leaves nothing behind. None of the new hosts (`get_player_position`/`set_player_position`/`set_player_respawn_position`, `give_item`/`take_item`/`item_count`, `inv_add`/`inv_take`/`inv_count`/`inv_list`) takes a username: a block can only ever act on the player standing in front of it, which keeps the sandbox honest without inventing a permission system. Quantities are capped at the player stack cap (999) and a give and a take of the same item cancel to a single upsert.

**The break hook runs while the voxel still exists, and its data dies with it.** `on_break(player)` reads `block_state` and `block_inventory` before the cell is wiped, so it can still speak about what it was. Its state writes are deliberately dropped — the place is going away — and its store is never flushed: the post-run contents go to whoever broke the block instead. That is why the handout is the store as it stands *after* the hook ran; handing out the rows read before it would double-give a hook that moved items with `inv_take` + `give_item`. Memory, store, light column and the voxel itself then go in one batch. A hook that throws is logged and the break proceeds, and a script with no `on_break` is a no-op rather than an error (`missingEntryIsNoop`), so widening the contract cannot break published content.

**A teleport has to move the object's memory too.** The Durable Object relays presence from its own cached entries, so a Worker that only wrote `player_state` would have the client's next presence frame drag the player back to where the object still thinks they stand. `POST /move` (internal, Worker→object) updates the cached pose, zeroes its velocity and pushes a `move` frame to that player's sockets; the client replaces the body and keeps its look. Respawn reads the anchor from `player_state.spawn_x/y/z` (NULL = the surface spawn) and sends the same notify, so a corpse's body relocates for everyone else, not only for its owner.

**Presence identity is the session, never a frame.** Live measurement found every inbound `pose` naming `"someone"`: the object took the name out of the frame, and the client sent `username || "someone"`, so any number of session-less sockets shared one identity — one avatar for several players, and the first of them to leave removed it for everybody. The router now authenticates the upgrade and stamps the account into an internal `x-ac-user` header, deleting whatever the browser sent (a Durable Object is reachable only through this Worker, so the header cannot be forged from outside); the object binds socket→name once at `accept`, falling back to a unique `guest:<uuid>` token. `pose` frames no longer carry identity, only pose. That also removes the client-claimed-name hole the PvP `target` field still relies on: an attacker can name a victim, but can no longer rename itself. Identity is fixed at handshake and lives only in headers, so the client has to re-handshake when it signs in or out (`liveReconnect`): the page opens its socket on boot, before anyone has signed in, and the same socket would otherwise carry that guest token for the whole visit — which is exactly what the next measurement showed.

**A new player gets a spawn column of their own.** Every account without a saved position used to wake at the same cell, so the other player's body stood inside your camera — "other players never appear" with a healthy socket. Join and anchor-less respawn now derive a column from a hash of the account over a ring around the origin, accepting only ground as flat as the origin's (`SPREAD` in `frontend/dve/src/main.js`, `SPAWN_SPREAD`/`spawnColumn` behind `defaultSpawnState`). No player-player collision was added: bodies still pass through each other by design; the fix is that they no longer start in the same place.

**Death is remembered per socket; health belongs to the account.** Live measurement: both tabs visible, both sockets open, both still *sending* pose frames (<400 ms old), and neither peer received a single one for ninety seconds. The object's entry for that account carried `dead:true` while the stored row held full health — a second socket for the same account (another tab, a reconnect that overlaps the one it replaces) had re-persisted the health it loaded, and the death flag on the older entry was never reconciled. The stored row is the authority, so a `pose` frame arriving from a dead-looking entry re-reads it (throttled per account) and, if it is above zero, `reviveAccount` clears the flag on **every** entry that account owns and pushes `respawn` plus `up` — for the peers and for the player's own screen, which is still showing a death overlay over a body that is no longer dead. An account that really is down reads zero and stays frozen until the death screen's Respawn button calls the same revive on purpose. The invariant: `dead` is a cache of the health row, never a second source of truth.

**The bed is a script, not a feature.** Sleeping to move your spawn point needed no server work: the respawn anchor (`player_state.spawn_x/y/z`), the host hook `set_player_respawn_position` and the respawn path that prefers it all already existed, so the bed is a row in `migrations/0017_bed.sql` whose Lua says "anchor me, then say so". It is the first built-in whose behaviour is authored content rather than engine code, and the anchor deliberately outlives the block: there is no unset move, the break credits the bed back, and a new bed moves the anchor again.

**The day is a phase, not a simulation.** Un-dialled, every client derives the same phase of a 24-minute day from its own wall clock: no traffic, no authority, no way to be a minute out from a neighbour. The admin's dial is the only thing that makes that phase world state, so it stays minimal — one row (`phase`, the real-world moment it was dialled at, `running`), one `time` frame broadcast on change, and the same frame handed to a socket the moment it connects. A push alone was not enough: a socket that missed the frame — reconnecting, or a published client too old to have a `time` branch at all — stayed in the old hour forever while the admin saw the new one, so clients also *pull* the row (`GET /api/time`) at join, on reconnect, and when the dial is opened. Clients derive `phase + elapsed`, or hold `phase` while stopped, so a stopped cycle needs no heartbeat per client, a resume carries on from where it stopped instead of jumping back to the sun, and deleting the row hands the world back to the sun. The dial lives in its own dialog, opened with **+** and offered only to the admin account (the server answers 403 for anyone else); admin controls are kept out of the pause menu on purpose, so the menu every player opens is the same menu and a player pressing a "secret" key gets a toast instead of half an admin panel.

**Real light lives in the section, filled by our own worker.** The voxel shader already decodes light from per-vertex nibbles (daylight plus coloured light) and the mesher writes them out of `Section.light`, a grid the world thread owns. So lighting needed no fork: the world worker registers a light table from the block registry — which voxel ids carry `light > 0`, which are see-through — and on its existing 500 ms maintenance pass stamps daylight down every column at full strength to the first full cube — vlox's own `WorldSun` semantics, with the section above's border value taking over where a section loads — and only then lets it fall into shadow at two levels per block, while block light spreads one level per step. Stop at full cubes only, plus anything the registry calls `transparent`, which is what makes a glass greenhouse lit inside. The emissive "glow cube" stand-in was deleted rather than kept alongside: it faked brightness with extra meshes while leaving the cells around the lamp dark, which is the opposite of what a lamp is for; a scripted light column keeps its column mesh because it *is* a column of light, drawn as an overlay. One trap cost hours: `WorldSpaces.voxel.getIndex` is dead code in the vendored build (a five-argument call into a six-parameter function, so every write landed at `NaN` and indexing silently did nothing) — section grids are addressed by the shift form in `Math/WorldIndexing.js`, the same one the mesher reads, and must be re-derived per call rather than cached at module scope.

**A world is a scope, not a deployment.** "Which server" used to mean exactly one thing: which API origin the page talks to, the published Worker or a local `wrangler dev`. That is still the only deployment switch. A created world sits *inside* one API: a `server_id` column on the world's tables (`world_edits`, `world_log`, `block_beams`, `block_state`, `block_inventory`, `world_clock`, `player_state`), widened unique keys, and one Durable Object per world (`idFromName(server)`), so presence, mob simulation and the clock frame cannot leak between worlds. `global` is implicit — no row, no `server` field, byte-for-byte the old request — so a stale client, an old bookmark or a curl probe keeps working, and the shared world is not a special case in the code. Visibility is enforced where the data is, because a browser page cannot accept an inbound connection: `private` compares a SHA-256 hash of the browser's random `X-AC-Device` key, `lan` compares the requester's IP /24 in RFC1918 space against the address the creator was seen at, and `public` means "anyone who can reach this API" — which for a player who wants to carry their own traffic means serving the page and API from their own machine and forwarding the port, stated in the create dialog in those words rather than promised. The registry is deliberately *not* scoped: blocks, items and recipes are content the whole site shares, and a private world is a private build, not a private mod pack.
