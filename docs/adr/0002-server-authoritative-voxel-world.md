
## Amendment — menu-first boot, presence, namespaces, day/night, cascade delete (2026-11-07)

**Boot is the main menu; the game view is lazy and stays live.** `Join global server` imports the DVE bundle, fetches registry + edits, and creates the view; the player's last pose is restored from `player_state` (persisted every 2 s while moving). `Main menu` from the pause dialog hides the game but keeps the engine and socket alive — rejoining skips re-init and just re-grabs the cursor. Cursor hand-off is explicit (HUD "Grab cursor" button; any closed dialog that leaves no dialog open re-grabs).

**Player blocks are `player:USERNAME:NAMESPACE:BLOCKNAME`** (four segments, exactly like `builtin:` ids); the display name is the separate `name` column. `POST /api/blocks` takes a `namespace` (optional, default `default` for old cached clients); migration 0007 rewrote existing 3-segment ids. **`DELETE /api/blocks/:id` cascades**: placed copies are removed from `world_edits` (terrain restored, broadcast as `air` over the WS), referencing recipes are dropped, inventory stacks are purged — deleting one's test block never requires manual world cleanup.

**Presence rides the existing `/api/world/live` WorldLive object:** clients post a `pose` frame (~4 Hz) with their username; the object keeps a socket→pose map and fans `pose`/`leave` out to the other sockets (a `who` frame pulls the roster). Avatars (blocky body + name card, lerped) are rendered client-side from these frames — presentation only, still no server physics, and a hidden tab's rAF halt freezes its render loop (avatars hold position until the tab is visible).

**Day/night is a deterministic epoch clock** — `Date.now() % 24 min` drives sky colour and an image-processing brightness scale; no sync traffic. **Glowing blocks** (registry `light > 0`) render through a Babylon GlowLayer emissive cube on the cell, not the vlox light pipeline (which stays off; faces would multiply by empty light data). **Generator workers keep every server edit including `air`** and receive live `note-edit` relays, so blocks mined before joining — or in cells that activate late — never render solid.

## Amendment — occlusion fix, saved appearance, recipe ownership, admin grant tool (2026-11-07)

**One rendering group for everything.** vlox renders its voxel sections in Babylon rendering group 1 and Babylon clears the depth buffer between groups, so any mesh left in group 0 (the avatars and glow cubes were) is painted over by voxels that sit *behind* it — the reported "players are only visible when nothing is behind them". Every mesh this app creates now joins `VOXEL_GROUP = 1` in `frontend/dve/src/main.js`. This is an invariant for future meshes, not a tuning knob.

**Character appearance is stored and rides presence.** `player_appearance` (migration 0008, widened by 0011) keeps one `#rrggbb` colour per user (`body_colour`/`head_colour`/`accent_colour`/`eye_colour`), written by `POST /api/player/appearance` and returned by `GET /api/player/state`. Every `pose` frame carries it; the WorldLive object sanitizes it to exactly those four keys before storing/relaying, so presence stays presentation-only. The in-game **C** dialog shows the signed-in username and the four colours; **I** opens the inventory.

**Recipes are owner-managed like blocks.** `GET /api/recipes` returns `creator`; `PUT /api/recipes/:id` and `DELETE /api/recipes/:id` are creator-only and reuse the POST validator verbatim (`recipeFieldsFromInput`), so an edit cannot smuggle fields a create would reject.

**Test-item grants are admin-only in the UI.** The "Add test items" form in the inventory dialog is hidden unless the signed-in username is `admin` (the handler refuses too). Server-side the endpoint is still per-account; real economies come later.

**Escape opens the pause menu in one press.** While pointer-locked Chrome consumes Escape itself (it exits the lock and delivers no keydown), so `openPause()` is driven from the `pointerlockchange` handler — gated on "game visible and no dialog open" so closing a menu never re-opens the pause menu.

## Amendment — items with programmes, sky bodies, mob simulation, health (2026-11-07)

**Items are what a player holds; blocks are what occupies a voxel.** Migration 0009 adds `items`: a `kind` (`block`/`tool`/`weapon`/`food`/`material`), declared stats (`damage`/`speed`/`heal`/`durability`), and `place_block_id` — a placeable item's *programme*, the single block it drops. Creators author an item the same way they author a block (`player:` namespace, creator-only `PUT`/`DELETE`, built-ins immutable). Like block behaviour, the programme is declarative data, never code (ADR 0001 staging). The two registries stay separate on purpose: `blocks` remains the voxel identity used by `world_edits`, `world_log`, textures, and placement rules — the item layer only decides *which* block a held thing writes. So `POST /api/world/place` validates the item (a `kind='block'` item with a programme, else `code:"not_placeable"`), runs the placement rules against the **block** row, debits the **item** stack, and stores the **block** id; `POST /api/world/break` credits the item whose programme is that block (built-in preferred). Deleting an item cascades its inventory stacks and referencing recipes.

**Sky bodies live in rendering group 0 on purpose** — the deliberate inverse of the avatar/glow/mob `VOXEL_GROUP` rule. The sun and moon are unparented emissive billboards on an infinite-distance root that orbits a 0.41 rad tilted axis from the same 24-minute epoch clock as the sky colour; because Babylon clears depth between render groups, group 0 draws *behind* every voxel, which is exactly what a sky body needs. Distance is derived from `camera.maxZ` so render-distance changes never clip them.

**Presence carries velocity and receivers dead-reckon.** `pose` frames now include `vx,vy,vz` (blocks/sec, clamped server-side to ±30). Receivers coast the avatar along that velocity for at most 0.6 s between frames, ground-clamp the extrapolation with the local terrain mirror when near the local player, and refuse an extrapolation that would engulf the camera — so 5 Hz presence reads as continuous motion, and a frozen sender pins in place rather than running away.

**Mobs are simulated inside the `WorldLive` object, ticked by alarms.** Durable Objects have no timers, so the loop is `ctx.storage.setAlarm(Date.now()+250)` re-armed at the end of each `alarm()` while at least one socket is connected (and never armed when the room is empty). The object keeps at most 12 mobs on the terrain surface: hostiles (`zombie`) steer toward the closest living player within a **40-block sphere** and hit once per ~1.2 s when the **3D** gap closes to 1.8 blocks — every range test uses `hypot(dx,dy,dz)`, so a player standing above a mob is out of reach even when their columns coincide, while the mob's *steering* stays horizontal because it walks the surface; peaceful mobs (`pig`) wander on a 3–6 s heading timer. Clients receive **full snapshots** (`{type:"mobs",mobs:[…]}`, ~4 Hz) rather than deltas, so one dropped frame self-heals, and only lerp toward them — no client-side mob physics exists.

**Health is owned by the server, and the single source of truth is kept across the REST/DO boundary.** `player_state.health` (migration 0010) is written by the object when a mob lands a hit and by `POST /api/player/respawn` / `POST /api/player/eat`. Those REST handlers write D1 *and* notify the running object through an internal `fetch` on the same DO id, which pushes a `respawn`/`health` frame to that player's sockets — otherwise the object's cached presence health would overwrite the REST write. Death marks the presence entry `dead`: hostiles stop chasing and stop damaging, and the client's hearts/death screen are pure projections of these frames.

**Attacks are claimed by the client but bounded by the object.** A client sends `{type:"attack",mob_id,item_id}`; the object rejects anything that is not a `weapon`/`tool` item, takes the damage from the `items` row (never from the client), and requires the player to be within 6 blocks of the mob. Killing credits a drop to the killer's inventory. This is the same trust posture as the rest of the prototype (movement stays client-side): the object validates *kind, stat, and distance*, not the swing.
