# All Contribute (prototype)

A Minecraft-like, browser-based MMO prototype with player-authored blocks and recipes.

## What this is

- Static frontend suitable for GitHub Pages.
- Cloudflare Worker API at `https://all-contrib.all-contrib.workers.dev`.
- Cloudflare D1 database for accounts, block definitions, recipes, inventories and world edits; one Durable Object (`WorldLive`) fans out live world changes over WebSocket.
- Passwords are hashed with PBKDF2 (never stored in plaintext; 100,000 iterations due to the Workers Web Crypto limit).
- Authentication uses Secure, HttpOnly, SameSite=None, Partitioned cookies rather than JavaScript-readable bearer tokens.
- Sessions expire after 7 days without an authenticated API request, or 30 days after sign-in, whichever comes first.
- Players can inspect active sessions and revoke other devices; logout revokes the current session server-side.
- Built-in blocks (`builtin:stone`, owner `admin`) cannot be edited; custom blocks can only be edited by their creator.
- A block/recipe definition is validated as data, not executed as arbitrary JavaScript. Placement behaviour is declarative (`rules_json`: `support` + `incompatibleWith`); conflicting blocks refuse placement or break, they never crash the game. See `GLOSSARY.md` and `docs/adr/0001-staged-behaviour-model.md`.
- **Server-authoritative shared world**: the world is a 3D voxel volume addressed by `(x, y, z)` (y up from bedrock). Base terrain — height-map over x/z, layered soil columns, caves, trees — is deterministic and byte-identical in Worker and browser (`backend/src/terrain.ts` mirrored in `frontend/dve/src/world.js`); only player edits are stored (sparse). Placing/breaking goes through the API with 3D occupancy and support validation; a WebSocket via the `WorldLive` Durable Object pushes edits to every connected client, with `world_log`-cursor polling as fallback — that log is a bounded catch-up queue, pruned to the newest 100 edits, because the sparse overlay already carries everything older. See `docs/adr/0002-server-world-before-dve.md`.
- **Fullscreen 3D game via Divine Voxel Engine (DVE)**: the page opens on a main menu; **Join** boots a first-person voxel game rendered with Babylon.js (`@divinevoxel/vlox` + `vlox-babylon`). WASD movement under gravity with **Space** to jump (voxel AABB collision), mouse look (pointer lock, drag-look fallback), a hotbar (1–9, then 0), crosshair targeting, **Backspace** for a third-person camera behind your own body — the body it draws wears the account's saved colours and holds the item its owner selected, the same picture every other player gets; **Esc** opens a pause menu hosting settings, inventory, character, studio, and account, the same menu for every player, while **Resync world** and the sky dial live in an **admin settings** dialog opened with **+** and shown to the `admin` account alone (resync re-runs the edit table so the server, the clients and the database agree again; see the API list). Every 3D click goes through the identical `POST /api/world/place|break` round-trip in `(x, y, z)`, and voxels are painted **only** from server-echoed edits over the WebSocket. If WebGL is unavailable the loading overlay reports it. See `frontend/dve/` below.
- **Creator studio for authors**: in-game (press **B**) you create **blocks** (hardness, light, colour, behaviour, support/incompatibility — `behaviour` is one of `solid`, `transparent` (light passes through it), `glowing`, `decorative` or **`useful`**: a block meant to be *used*, the bed setting your respawn and the beacon switching its light column) and **items** — the item is what the player holds, and a placeable item is *programmed* with the block it drops into the world (`place_block_id`). Both can be edited and deleted by their creator only; built-ins are immutable. A published block may also carry an uploaded PNG **texture** (a ≤60 kB data URL), one of the ten built-in **models**, and a **Lua script** for in-world interaction; an item may carry an uploaded **icon** (≤40 kB). `GET /api/blocks` returns `models`, so the Studio can only offer what the renderer actually implements. See `docs/adr/0001-staged-behaviour-model.md`.
- **Items, tools and weapons**: the `items` registry holds kinds `block` (places a block), `tool` (mining speed), `weapon` (attack damage), `food` (heals), `material` (crafting only), each with declared stats — never code. Built-ins seed a pickaxe/axe/shovel, a sword, an apple, a stick, planks and one placeable item per built-in block.
- **Scripted blocks (Lua, server-side)**: a custom block can carry a Lua script run inside a sandbox (`backend/src/lua.ts`) — instruction and wall-clock budgets, no `os`/`io`/`require`, no network, no access to anything but the arguments. `on_interact(player)` runs when a player presses **E** with the crosshair on that block and may return a menu (a table, or by calling `menu()`); the client shows it, and the chosen `key` is dispatched to `on_choice(key, player)`. A script's memory is per world cell (`block_state`), so two beacons never share a setting. `beam(colour)` paints a light column from the cell to the top of the world: it is server state (`block_beams`), broadcast to everyone over the live socket and replayed to new joiners by `GET /api/world` (`beams`). The built-in `builtin:beacon` is written this way (migration 0013) — the shipped content proves the contract instead of a hard-coded special case. A script that throws is reported to the player as a broken block, with the interpreter's message, rather than leaving the key press looking dead. Every script also sees its own cell as the globals `x`, `y`, `z`. A block can speak as it dies: `on_break(player)` runs during a break, **before** the cell is wiped, so the hook still reads its own memory (the built-in beacon puts its column out and says so); its toasts ride back in the break response and the client shows them. A script can move the player who pressed the key — `get_player_position()` (three return values: `x, y, z`), `set_player_position(x,y,z)`, `set_player_respawn_position(x,y,z)` (the anchor `POST /api/player/respawn` wakes them at) — and it can handle items: `give_item`/`take_item`/`item_count` on that player's bag, plus a store of its own in the cell (`block_inventory`, migration 0015) through `inv_add`/`inv_take`/`inv_count`/`inv_list`. When a cell with a store is broken, its contents go to whoever broke it (each stack capped at 999 — this engine has no ground drops) and the store is deleted with its memory and light column. None of these takes a username: a block script can only ever act on the player standing in front of it. Every effect is recorded during the run and written by the caller in one batch, so a script that fails partway leaves nothing behind.
- **Mobs, health and death**: the `WorldLive` object simulates up to 12 mobs on the terrain surface, spawning them automatically in a **ring 40-50 blocks around a live player** (never on top of them, never by request) and forgetting any mob that ends up more than 96 blocks from every connected player — otherwise a far-wandered mob squats the cap and the world stops spawning new ones. Hostiles (`zombie`) chase the closest living player inside a 56-block **sphere** (just past the ring, so a mob born at its far side still notices its player) and hit them within 1.8 blocks in 3D (the Y axis counts: a zombie standing under your feet cannot reach a player two blocks up), peaceful ones (`pig`) wander — and broadcast full snapshots every 250 ms. Chase/attack ranges are spherical, mob steering stays horizontal. Health (20 = 10 hearts) lives in `player_state.health`. A new socket never inherits a stored death: the object revives a stored 0 on the first health load and pushes a `health` frame, so the client's starting life always comes from the object rather than from the saved row (the row is a mirror, not a verdict). Hitting zero shows the death screen and releases the cursor, `POST /api/player/respawn` restores you and takes the cursor back. Weapons/tools attack mobs (6-block reach, also spherical), food heals (`F`). Left-click aimed at a body attacks instead of digging: an armed swing uses the item's declared `damage` at 6-block reach, bare fists do 1 at 3.5-block reach, and players are valid targets — the object re-checks distance and rate-limits the swing, never the claim of who was hit. Whoever lands the killing blow is named on the victim's death screen, a struck body flashes white in every client (`hit` frame), and a dead body lies down until its owner respawns.
- **Customisable avatars**: four saved colours per account — head, body, legs and **eyes**. The eyes are two boxes on the front of the head in the 3D avatar (and two dots in the character preview), so other players can read which way you are facing; they ride the presence frames and re-colour live. The look belongs to the account, so it arrives with the account: joining reads `GET /api/player/state` for it, and because Join also lets you sign in from inside the world, signing in while the world is already open re-reads the account and repaints your own body — otherwise a body built before you signed in keeps the plain default colours, which is what made third person look like it ignored your settings. The site has its own `favicon.svg` (an ink-outlined grass block under an amber sun, matching the paper-and-ink design system).
- **Sky**: an emissive sun and moon orbit on a tilted axis driven by the world's clock (the same 24-minute day as the sky colour), rendered in group 0 so terrain occludes them. That clock is the world's, not each browser's: by default it reads off the wall clock, and the admin can dial it — **Night / Dawn / Day / Dusk**, a slider, a switch that stops the cycle wherever it stands, and a button that hands the world back to the sun (`POST /api/time`, migration 0018). The dial sits in the **admin settings** dialog (**+**), which the client opens only for the `admin` account and the server refuses for anyone else (403); the pause menu holds no admin control at all, so a player pressing **+** simply gets a toast saying who does. Every screen agrees on the hour: the object pushes a `time` frame to every socket on each dial change and to each new socket at `accept`, and every client also *pulls* the row (`GET /api/time`) when it joins, when it reconnects, and when the dialog opens — a pushed frame can be lost, and one lost frame used to leave exactly one player in a different day.
- **Flat or textured, one switch**: Settings → **Look** is a single client setting, `flat` (default) or `detailed`. `flat` paints every block and item from its registered colour; `detailed` paints published blocks with their uploaded texture and model, paints a block's **upper face and underside from their own pictures** when it has any (`blocks.texture_top`/`texture_bottom`, falling back to the side texture), and shows uploaded item icons in the bag. It is one option rather than two so the block and item looks can never disagree, and it is a *rejoin* setting: vlox compiles its texture atlas when the world view is created. A block with no texture/model, a malformed payload, or a model the renderer does not implement falls back to the solid colour — `detailed` can never brick the view.
- **Client settings** (localStorage): sensitivity, FOV, render distance, movement speed, **Look** (`flat`/`detailed`; changing it needs a rejoin), and a server selector — the global production Worker or a local dev Worker (local option only over `http://`).
- **Server-side inventory**: stacks live in D1 per account; placing debits, breaking credits, crafting is validated and applied server-side. Old browser-local stacks are uploaded once per account automatically. The bag is a 2D grid and the hotbar is its **first ten slots** (keys **1–9**, then **0**) — one list, two views. Dragging one stack onto another (mouse) **swaps** their places, in the bag and in the hotbar; the arrangement is per account (`inventories.ord`, migration 0014, written by `POST /api/inventory/order`), so it survives a rejoin. Accounts that never drag keep the old alphabetical order. Touch devices keep click-to-select. The selected item is read out at the screen's bottom-right, just above the hotbar row: its uploaded image when the registry carries one, its colour otherwise — and the same image paints the small cube in every player's hand, including your own body in third person. Granting items (`/api/inventory/add|remove|clear`) is restricted to the `admin` account **server-side** — 403 for everyone else, not just hidden in the UI.

This is a starter project, not a production MMO. It lacks authoritative movement (physics is client-side presentation over the deterministic mirror), anti-cheat, rate limiting, moderation, and production-grade account recovery.

## 1. Prepare the D1 database

Install Node.js (LTS), then:

```bash
cd backend
npm install
npx wrangler login
```

### New or current databases

Create the database (new only):

```bash
npx wrangler d1 create all-contribute-db
```

Wrangler prints a database ID. Put that ID in `wrangler.jsonc`, replacing `REPLACE_WITH_D1_DATABASE_ID`. Then apply the migrations (this records them in D1's migration ledger, so future `wrangler dev`/`deploy` runs know the schema is current):

```bash
npx wrangler d1 migrations apply all-contribute-db --remote
```

`migrations/0001_init.sql` is a copy of `schema.sql` — the cumulative table definitions and built-in block seed. It is idempotent (`CREATE TABLE IF NOT EXISTS`), so it is safe even on a database already provisioned from `schema.sql`.

### Databases older than the rebased baseline

The migration chain was rebased: the earlier one-time migrations (session lifetimes, `minecraft:` → `builtin:` rename, world/inventory tables) are folded into `0001_init.sql`. A database already at that history needs no action — applying `0001_init.sql` matches nothing. A genuinely ancient database (before those changes) is not auto-upgraded by the baseline: recreate it (`wrangler d1 delete` + `create` + migrations) or add the missing pieces by hand (`sessions.session_id`/`idle_expires_at`/`last_seen_at`, `blocks.rules_json`, `inventories`/`world_edits`/`world_log`, `builtin:` rename).

The new Durable Object (`WorldLive`) needs no database work: `wrangler deploy` provisions it from `wrangler.jsonc`'s `migrations` entry. If you deploy onto a Worker that previously ran the Cloudflare template's `MyDurableObject`, the stale class blocks new deploys; the clean fix is `npx wrangler delete --name all-contrib` followed by a redeploy (D1 data is a separate resource and survives).

### World model v2 (`0005_world_3d.sql`)

The world moved from a 2D grid to true 3D `(x, y, z)` coordinates. `0005_world_3d.sql` drops and recreates `world_edits`/`world_log` with a `z` column and y-up semantics, and seeds the two new built-in blocks (`builtin:leaves`, `builtin:bedrock`). Old 2D-era edits do not translate to the new coordinate system: **applying 0005 to a deployed database resets the shared world** (accounts, blocks, recipes and inventories are untouched). Accounts that placed blocks before the upgrade keep their inventories but wake up in the new terrain.

### Scripted blocks, textures and bag order (`0012`–`0015`)

All four are additive — no data is rewritten, a deployed database keeps its world and inventories:

- `0012_appearance_scripts.sql` — `blocks.texture`/`blocks.model`/`blocks.script`, `items.icon`, and the two script tables: `block_state` (a script's persistent per-cell key/value store) and `block_beams` (the light columns a script switched on, cached so a joining player sees them without re-running Lua).
- `0013_beacon_script.sql` — seeds the built-in beacon's Lua, so the shipped world proves the script contract instead of special-casing the beacon in code.
- `0014_inventory_order.sql` — `inventories.ord`, the per-account bag/hotbar arrangement. `NULL` means "never arranged": those sort last by item id, which is the pre-existing behaviour, so no backfill is needed.
- `0015_script_inventory_and_respawn.sql` — `player_state.spawn_x`/`spawn_y`/`spawn_z` (a block script's respawn anchor for that account; `NULL` = the surface spawn, which is what every existing row already is), and `block_inventory` (a scripted block's per-cell item store, `quantity` 0–999, keyed `(x,y,z,item_id)` — the same cap as a player stack, because a cell's contents are handed straight to whoever breaks it). It also rewrites the built-in beacon's Lua to add its `on_break` hook, so the shipped content keeps proving the script contract as the contract grows.

### Shipped art, the bed, the world's clock and real light (`0016`–`0023`)

All additive again — a deployed database keeps its world:

- `0020_bed_face_textures.sql` — the bed names a picture for its upper and lower faces too, like grass and wood already do: from above the cover with the pillow at the head end and the frame as a rail around the edge; from below the slatted frame over a dark gap.
- `0021_bed_side_texture.sql` — the bed's side, redrawn. The old picture filled the whole face with cover, which read as a red wall with a pillow stuck to it; the face now has a silhouette — headboard, footboard, mattress edge-on between them, frame rail and legs underneath, open space above the mattress. The item icon is the same drawing enlarged, so the bag and the block agree.
- `0022_useful_behaviour.sql` — a fifth block behaviour, **`useful`**: a block that responds when a player uses it (the bed sets your respawn, the beacon switches its light column) instead of only sitting in the world. The `behaviour` CHECK cannot be widened in place, so `blocks` is rebuilt with its live column list; `items.place_block_id` references `blocks(id)` and a D1 migration cannot disable foreign keys, so `items` is rebuilt once without the link, `blocks` is rebuilt with the widened CHECK, then `items` is rebuilt again with the link restored. The built-in bed and beacon become `useful`.
- `0023_builtin_owner.sql` — built-in blocks and items are stamped `creator_name='admin'` instead of `'SYSTEM'`: the site has a real admin account, so the Studio card credits that account for shipped content. Nothing gates on the name (ownership checks use `creator_id`, still NULL for built-ins), so this is display only.

`behaviour` is a *category* the Studio and the registry show; what a block actually does on use is still its Lua script (`on_interact`/`on_break`), so `useful` declares intent, it does not grant capability.

- `0016_builtin_textures_and_icons.sql` — paints the built-in registry: a 16×16 PNG in `blocks.texture` for every built-in block and a 32×32 picture in `items.icon` for every built-in item, as base64 `data:image/png` data URLs in exactly the shape a Studio upload writes (so built-ins and player content travel through one code path).
- `0017_bed.sql` — the `builtin:bed` block, its placeable item and icon, and its Lua: `on_interact` sets the sleeper's respawn anchor and says so. The built-in world proves the script contract again rather than hard-coding a bed in code.
- `0018_world_clock.sql` — `world_clock`, one row: the admin's dialled phase, the real-world instant it was dialled at, and whether the cycle is running. Absent means the sun runs off each client's wall clock, which is why an undialled world costs no sync traffic.
- `0019_block_face_textures.sql` — `blocks.texture_top`/`blocks.texture_bottom`, and the built-ins that need them: grass a bladed top and bare soil underneath, wood the cut end on both. Two `ALTER`s plus seeded images; a block whose six faces are one picture is left alone.

### Your own worlds (`0024`)

`0024_servers.sql` is a re-key, not a data loss: a `servers` table plus a `server_id TEXT NOT NULL DEFAULT 'global'` column on the seven world tables (`world_edits`, `world_log`, `player_state`, `block_beams`, `block_state`, `block_inventory`, `world_clock`), and every unique key widened to lead with it. Existing rows keep `global`, so the shared world is byte-for-byte what it was and no request path has to name it. Apply it and deploy in the same step: the new code reads `server_id`, so old code beside a widened schema (or new code beside an un-widened one) is broken. `world_log.seq` stays monotonic across worlds — only rows inside one world's view are ever compared — and the per-world trim keeps each world's newest `WORLD_LOG_KEEP` rows. `inventories` is deliberately **not** scoped: your bag follows your account between worlds.

Deploying also resets the **live** world object: an idle `WorldLive` instance is evicted by `wrangler deploy`, which drops its in-memory mob population, presence, health and beam caches. Nothing in D1 changes — the world's blocks, clock, positions and inventories survive exactly as they were.

### Drop spec, sea level and crops (`0025`–`0027`)

- `0025_drop_spec.sql` — `blocks.drop_item_id`/`blocks.drop_qty` (1–99). A block's drop is now its own declaration, not just its programming item: `NULL` keeps the implicit behaviour (breaking a block hands out its programmed item, qty 1), an explicit pair replaces it. The Studio form exposes both; the break route resolves the spec server-side and the qty is clamped there, never trusted from a client.
- `0026_water.sql` — registers `builtin:water` (transparent, unbreakable-by-design drop NULL, 16×16 face + 32×32 icon seeded with the same per-pixel PNG recipe as `0016`). With the terrain rule change (`SEA_LEVEL = 10` in `backend/src/terrain.ts` and its frontend mirror), every column whose ground sits below sea level fills with water up to `y = 10` and its surface cell becomes sand — beaches come out of the height function for free. The sea is static: no flow, no simulation, no drowning. The client swims: inside a water cell gravity drops to a quarter and Space becomes a slow upward drive.
- `0027_farm.sql` — `builtin:farmland` (soil, placed directly — there is no hoe) and the four `builtin:wheat_N` stages on the existing crossed-panels model, plus the `wheat_seed` (places `wheat_1` on any solid surface) and `wheat` (food, heals 2) items. Wheat carries the Feature-1 drop spec: stages 1–3 break for one seed (replanting is free), stage 4 for two wheat. Growth is the `WorldLive` alarm's `stepCrops` pass: every ~20 s at most 32 standing wheat cells advance one stage; the cell's `created_at` is the clock, so no extra column exists and a re-planted cell restarts honestly. Growth writes land with the original `placed_by` (or NULL) and log like any edit. Crops only advance while at least one player holds the world object awake (the alarm's precondition), which matches the mob tick.

## 2. Deploy the API

The Worker name is configured as `all-contrib`. When updating an existing installation, **keep your existing `wrangler.jsonc` and its real D1 `database_id`**; do not replace it with a copy containing the placeholder ID. Deploy:

```bash
npx wrangler deploy
```

Expected API origin:
`https://all-contrib.all-contrib.workers.dev`

If Cloudflare gives you a different URL, update `API_BASE` in `frontend/app.js`.

## 3. Publish the frontend on GitHub Pages

Put the contents of `frontend/` in the root of a GitHub repository (or configure Pages to publish that folder using a supported workflow). Include the pre-built `frontend/dve/dist/` directory — the 3D bundle is committed, so Pages needs no build step. Simplest:

1. Create a repository named `all-contribute`.
2. Copy `frontend/index.html`, `frontend/styles.css`, `frontend/app.js`, the whole `frontend/dve/` folder and the whole `frontend/vendor/` folder into its root.
3. GitHub → Settings → Pages → Deploy from a branch → `main` → `/ (root)`.
4. Wait for the Pages URL to appear.

The frontend has no build step. `frontend/vendor/monaco/` (~4.9 MB, the trimmed minified Monaco `vs` tree — editor core + basic languages, no TS/HTML/CSS language features) backs the Studio's Lua editor; it loads lazily (first focus in the block form) and the plain textarea is the fallback if the payload fails to load.

### Rebuilding the 3D bundle

Only when you change `frontend/dve/src/`:

```bash
cd frontend/dve
npm install          # once; pulls @divinevoxel/vlox + vlox-babylon + babylonjs
npm run build        # esbuild → frontend/dve/dist/ (commit the output)
```

`npm run build` also writes `dve/dist/rev.js` (a committed build artifact) — content hashes of every bundle — and both `app.js` and the view import/bundle their scripts as `?h=<hash>`. Without that, GitHub Pages' caching pins whatever `dve-view.js` a browser first fetched, and a stale bundle throws at calls only newer app.js makes (e.g. `grabPointer is not a function`). Run the build **twice** after changing sources: the first pass seeds the manifest the second pass inlines. Bump `?v=` on `app.js`/`styles.css` in `index.html` when app.js changes.

Known limitations of the 3D game:

- Block textures are compiled once when the game view is first created; publishing a new block mid-session paints with a placeholder color until the page is reloaded.
- Built-in blocks and items ship real pixel art: `blocks.texture` (a 16×16 PNG face) and `items.icon` (a 32×32 picture) hold base64 `data:image/png` URLs in exactly the shape a Studio upload produces, seeded by `backend/migrations/0016_builtin_textures_and_icons.sql`. `blocks.texture` is the block's **four sides**; the nullable `blocks.texture_top`/`texture_bottom` (migration `0019_block_face_textures.sql`) picture the **upper face and underside** separately, and fall back to the side texture when empty. The built-ins that need it carry it: grass a bladed top and bare soil underneath, wood the growth rings of a cut log on both ends — the shipped grass block is why the columns exist, since painting its sides on top and bottom read as a bug. Only the plain cube is swapped to the engine's six-texture model when a block names a top or bottom; shaped and transparent blocks keep their own model. Only **detailed** mode compiles them, so flat mode — and any client that cannot decode the image — still paints the registry `colour`; that is why the colour columns stay mandatory. Glass is painted as a pale window rather than drawn with transparency, because the voxel material this engine builds is opaque.
- The client renders a 256×32×256 walkable field (`SLAB` in `frontend/dve/src/world.js`; camera clamped to its lip). The generator focus follows the player: `main.js` posts `move-generator` whenever the player crosses a 16-block cell and vlox re-rings its active sectors — chunks generate ahead and drop behind. The generator runs render 48 / generation 96 / max 96, so generation spans the entire active ring and no sector ever sits on a generation boundary. The API is looser — `worldCoords` accepts x/z in ±1,000,000 and y in 0..31 — so the region is a rendering/authority convention, not a storage limit.
- Terrain is byte-identical in `backend/src/terrain.ts` and its mirror `frontend/dve/src/world.js`. Changing it means changing both in lockstep — a desync renders one terrain in the head and edits validated against another (the generator fetches only sparse edits from the API).
- Walking physics is client-side presentation: gravity, Space-jump, and voxel AABB collision run in `main.js` against the client's authoritative cell mirror (synced `worldEdits` + the `terrain.ts` mirror). The server validates block edits, never the player's body. No step-up (a one-block ledge needs a jump), no fall damage; blocks pushed into the player by other players' edits only pop them up if the block rises into their feet.
- Stock vlox 0.0.72 deadlocks its generation/lighting queues at fixed-radius borders and wedges its Builder `paint-voxel` task (`LockSectors` awaits sectors checked out for mesher transfer forever; the world thread's voxel palette lands at an offset); `frontend/dve/src/world.worker.js` carries the compensations — the `driveSlabPipeline` link-and-flag maintenance driver, `shiftLUTToPalette` LUT re-alignment, and a `paint-direct` simulation-brush task used by `applyEdit`. That palette is also *incomplete*: only names the generator actually touched get a record slot, so a block the terrain never produces (`builtin:beacon`, any published block) decoded to composite id 0 — air — and `Brush._paint` wrote air with no throw, no error frame, nothing. `frontend/dve/src/lut-repair.js` calls an entry usable only when its record slot decodes back to its own palette name, and repairs the gap **without inventing new ids**: composite ids are positional, so a thread that allocates its own writes numbers the others read as different blocks (live symptom: the dig named the placed block while the pixels showed terrain through it, and the mesher aborted the section build). The module instead aligns the imported composite ids with this thread's palette slots, duplicates each entry's trueId-keyed encoding onto its composite index (vlox reads `modelsIndex` by composite id while meshing), mirrors what the payload left out from a same-name entry and rebuilds missing `VoxelTags`; main, world, generator and mesher all run it the moment `sync-data` lands and again every 2 s, so an id one thread wrote decodes in every other; `paint-direct` then reads the cell back through the brush's own cursor and reports the name it found, so a failed paint is a string instead of a hole. (Constructing a fresh `WorldCursor` inside a task handler wedges `runTaskAsync` forever — reuse the brush's cursor.) Do not "simplify" any of them without re-testing distant sectors and click-breaking placed blocks.
- A written voxel is not a drawn one: vlox rebuilds a section only when its `displayDirty` tick changes (`SimulationSector.tickUpdate`) and a brush write bumps nothing, so a placed block (or a dug hole) stayed invisible until the sector unloaded and reloaded. The bump has to land on the right object: `WorldRegister` exposes only `sectors` (a lookup from world coords to a `Sector`), the tick lives on the **Section** — `Sector.getSection(x, y, z)` takes world coords and derives the sector-relative index — and `Sector` has no `incrementTick` at all. A bump aimed at `WorldRegister.sections` (which does not exist) threw on every edit, was swallowed as "buffers detached", and parked every touched section in a capped retry queue forever: that is a broken block staying on screen until the page is reloaded. `paint-direct` bumps the touched section and its boundary neighbours — the neighbour section owns the shared culled face — and counts the bump as done only when the tick actually changed, because a write into a detached `tickArray` is a silent no-op; real failures ride the short retry queue for sectors checked out for mesher transfer.
- Three sites of the vendored `@divinevoxel/vlox` (tracked in `frontend/dve/node_modules`, bundled by `dve/build.mjs`) are repaired: the mesher's relational **state** builders are now guarded the way its mod builders always were (an unencoded palette id threw `reading 'position'` in the middle of a section build, which lost the `set-section` message — the edited section never reached the renderer — and mispaired the snapshot pool, whose returns are FIFO against a LIFO pop); `createAndTransferSnapShot` releases its 5×5 sector lock in a `finally` (a buffer detached during the hand-off skipped `UnLockSectors`, leaving those sectors locked forever so generation and re-meshing in the region stopped); and `SimulationSector.checkOut` skips a neighbour whose `Sector` object has been unlinked instead of throwing after it had already flagged and detached the earlier ones, which left `waitTillCheckedIn` unresolved and the build queue stalled.
- Under heavy CPU load (e.g. headless Chromium with swiftshader in CI) the mesher→main section deliveries can stall part-way through the initial build: the centre renders and pixel-proves fine, but far sectors may lag. This is vlox backpressure under starvation, not data loss.
- Presence avatars are presentation frames on the world WS (`pose` ~4 Hz carrying the saved appearance colours, `who` roster pull, 60 s staleness sweep). A hidden browser tab halts rAF, so a backgrounded player's avatar freezes in everyone else's view — cosmetic, and it self-heals when the tab is focused again. The DO sanitizes `appearance` down to the four `#rrggbb` colour keys; presence remains presentation-only and is never validated like a block edit.
- Presence **identity** is the session, never the frame. The router authenticates the socket upgrade and stamps the account into an internal `x-ac-user` header (deleting any client-supplied value first — a DO is only reachable through this Worker); the object names each socket once at `accept`: the account, or `guest:<8 hex>` for a session-less tab. Every `pose`/`roster`/`leave` frame carries that name, and the `name` a client puts in a `pose` frame is ignored. It used to be trusted: every socket whose client had no username fell back to `"someone"`, so several players shared one avatar and any one of them leaving deleted it from everyone else's screen. The stamp exists only in the upgrade headers, so the client re-handshakes the live socket whenever the account changes (`liveReconnect` in `app.js`, called from `setAuthenticatedUser`/`clearAuthenticatedUser`): the page boots its socket before anyone has signed in, and without the re-dial a signed-in player would be present under the guest id they happened to arrive with.
- A brand-new account has no saved position, and every such player used to wake up on the exact same cell — the other body standing inside your own camera reads as "other players never appear" while the socket is perfectly healthy. New spawns now take a column from a ring around the origin, chosen by a hash of the account and only where the ground is as flat as the origin's: `SPREAD` in `frontend/dve/src/main.js` (seeded by `spawnSeed` — the account, or a random per-tab guest token) and `SPAWN_SPREAD`/`spawnColumn` in `backend/src/index.ts` (`defaultSpawnState`, so anchor-less respawns spread the same way). A saved position always wins.
- The bed (`builtin:bed`, `backend/migrations/0017_bed.sql`) is a built-in block programmed in sandboxed Lua: pressing **E** with the crosshair on it calls `set_player_respawn_position` with the cell's eye position (centre horizontally, one block plus eye height above), which upserts `player_state.spawn_x/spawn_y/spawn_z` — the very columns the respawn endpoint already prefers and spreads. Nothing server-side had to be written for it. Breaking the bed deliberately does not clear the anchor (there is no unset move, and the drop hands the bed back, so a new bed moves the anchor again); sleeping is a toast, not a menu.
- Live frames fail loudly: `ws.onmessage` separates an unparseable frame (ignored) from one that parsed and then threw inside the view — `console.warn("live <type> frame failed: …")`. The old blanket catch hid a view-layer throw in the `pose` branch, which is "no players on screen" with nothing in the console.
- The live socket is best-effort: while it is down, edit frames, light-column removals and roster changes are simply missed, and no later frame can take something away — only the snapshot says "nothing here". So the app re-takes the world snapshot on every **reconnect** (`rebuildWorldFromSnapshot`, driven from the socket's `onopen` after the first open): the same path the admin's Resync button drives. It re-applies the edit map, repaints cells the snapshot no longer mentions with base terrain, and asks the renderer which columns it is actually drawing (`beamCells()`) rather than trusting the client's last-read list, so a light column whose removal frame was lost goes out without a page reload.
- Third person (**Backspace**, or the HUD button) is a camera-only mode: a second `FreeCamera` orbits behind the shoulders along the look direction, pulled in when a voxel would stand between the eye and the body, and only `scene.activeCamera` changes. The physics body remains `camera.position` (the eye camera) — movement, AABB collision, gravity, `pose` frames and crosshair picking all read it, so mining and placement behave exactly as in first person. The local body is built by the same `buildAvatar` the remote avatars use (no name card), lives in `VOXEL_GROUP`, is coloured by the saved `appearance` through `setSelfAppearance` (the view remembers those colours, so a body built after a late join still wears them), holds a cube in the colour of the selected item (`setSelfHeld`, fed the same way remote bodies are fed by `pose` frames), and is disabled in first person. So third person shows the player the body everyone else sees: their colours, the thing in their hand.
- Presence carries `vx,vy,vz` so receivers dead-reckon between frames (`advanceRemotes` in `frontend/dve/src/main.js`): extrapolation is capped at 0.6 s of velocity, ground-clamped, and refused when it would drop a prediction inside the local camera. It is smoothing, never authority — the next real pose wins.
- Mobs are simulated inside the `WorldLive` object on a 250 ms storage alarm and broadcast as full 4 Hz snapshots; clients only interpolate (`setMob`/`advanceMobs`) and a 5 s silence prunes the mesh. Nothing spawns a mob from the client: each tick adds one to the **40-50 block ring** around a random live player while the population sits under 12, and the same tick deletes any mob more than **96 blocks** from every connected player (a dead player's body still counts). Without that sweep a mob that wandered out of sight kept its slot forever and the world quietly stopped producing new ones — the "mobs never spawn" symptom. Mob `y` is the terrain surface from the `terrain.ts` mirror raised above recorded player edits, so a mob can hover over a column someone excavated or walk through a decoration it was never told about, and nothing pathfinds. Attacks are client-claimed (`attack {mob_id, item_id}`) and bounded by the object — the item must be `weapon`/`tool`, its `damage` from the items row decides the hit, and the mob must be within 6 blocks — never by who actually aimed.
- Health lives in `player_state` with the object as runtime source of truth (REST `respawn`/`eat` write D1 and notify the object over internal `fetch`); the object ignores a dead player's own `pose` frames, so the body freezes in place — but parking the local body is client presentation (`setFrozen`), the authority is the object. Death also releases the pointer lock deliberately, and the cursor stays free until respawn: the view's canvas `pointerdown` refuses to re-lock while the body is frozen, the menu-close re-grab and the Esc-opens-pause path both check that the death screen is hidden, and the full-screen death overlay hit-tests in front of the canvas anyway. `dead` is remembered per **socket** while health belongs to the **account**, so anything that heals the account behind the object's back — food, a second tab, another instance — can leave a healthy row next to an entry it still believes is a corpse: the player walks around a frozen body while every peer sees a body nailed to the ground, which is indistinguishable from "other players never appear". A `pose` frame from a dead-looking entry now re-reads the stored health (throttled per account) and, when it is over 0, `reviveAccount` clears `dead` on **every** entry that account owns and pushes `respawn` plus `up` frames. An account that really is down reads 0 and stays down until the death screen's Respawn button does the same thing on purpose.
- Items and blocks are two registries: `world_edits`, `world_log` and WS `edit` frames carry **block** ids, never item ids. An item's "programme" is declarative — `place_block_id` — not code. Placing debits the item and writes that block; breaking a cell credits back the first item that programmes that block (built-in first, then lowest id), so two different items that programme the same block credit deterministically but not as "the exact stack you placed".
- Every Babylon mesh this app adds (avatar parts, name cards, beacon beams) must set `renderingGroupId = 1`. vlox draws its voxel sections in group 1, and Babylon clears the depth buffer between rendering groups — a group-0 mesh is painted over by voxels that are *behind* it, which looks like players showing through walls. Keep new meshes in `VOXEL_GROUP` (`frontend/dve/src/main.js`).
- The day/night cycle is a phase, not a simulation. Un-dialled, every client picks the same phase off its own wall clock (`Date.now() % 24 min`) with zero sync traffic; the admin can overwrite that phase, stop the cycle, or hand it back (`world_clock`, one row, pushed as a `time` frame **and pulled** by every client at join, on reconnect and when the admin dialog opens — a push alone could be lost on a dropped socket, which left one player standing in a different day from everyone else). It is still only a phase — there is no server-side game calendar, and a client whose clock is badly skewed sees the sky shifted by its own offset.
- A block with a registry `light > 0` emits **real light**: the world worker fills each section's voxel light grid (`Section.light`, four packed 4-bit channels — sun, R, G, B) and the mesher bakes that grid into every face, so a lamp brightens the cells around it and a wall stops the light. Two channels: **sky** is stamped down every column at full strength (15) from the top of the section to the first full cube — exactly what vlox's own `WorldSun` pass does — or at the value the section above carries where one loads, and only then falls into shadow at 2 levels per block (vlox's `SunFallOffValue`); **block light** spreads 1 level per block from each emitting block. Light only travels through cells that are not full cubes — air plus blocks whose behaviour is `transparent`, which is why the inside of a glass greenhouse is lit. Main sends the two per-block facts (`light`, `transparent`) to the worker once per join, so a Studio-published lamp emits light the moment it is placed; every edit re-queues the touched sections and their six neighbours, and a section whose border values changed re-queues its neighbours, so the field settles across section lines. Emissive `GlowLayer` cubes are gone (the user asked for light, not glow); the layer survives only for beacon beams, and `light > 0` no longer means "bright object" but "light source". `baseLevel` is still 0.2, so an unlit cave is dim rather than black.
- A script-painted light column (`block_beams`) is an overlay, not light: one emissive column mesh per cell from the block up to the world ceiling, plus the server row that makes it survive a rejoin. It deliberately passes through terrain and casts no light on neighbouring voxels.
- Block scripts run inside the request that touches them (`POST /api/block/interact`): one bounded interpreter pass per call (20 000 instructions, 50 ms, no `os`/`io`/network) with per-cell state. That is enough for game logic and it can never run arbitrary JS, but it is not a hostile-multi-tenant sandbox and there is no per-author script quota.
- Arranging the bag/hotbar uses HTML5 drag-and-drop, which is mouse/trackpad only; on touch the tap-to-select path stays, and the swap is applied server-side (`/api/inventory/order`) in either case.

- `POST /api/world/place` `{x, y, z, item_id}` (session; the ITEM is validated: only a `kind='block'` item with a `place_block_id` can be placed — `code:"not_placeable"` otherwise — the placement rules run against that BLOCK row, the item stack is debited, and `world_edits` stores the block id. Refusals on `occupied`/`no_support`/`incompatible`/`no_item` debit nothing; the block's support rule is evaluated against the voxel beneath — `any` (the default, so a block dropped in mid-air stays) lets it stand, `solid` demands a filled cell below, `none` demands an empty one — and `incompatibleWith` scans the six neighbours)
- `POST /api/world/break` `{x, y, z}` (session; credits the ITEM that programmes the dropped block — `SELECT id FROM items WHERE place_block_id=? ORDER BY is_builtin DESC` — unless the block declares its own drop spec (`drop_item_id`/`drop_qty`, 1–99, resolved server-side), which wins even when it names an unrelated item like seeds; refusing empty voxels, unbreakable blocks such as bedrock (`code:"unbreakable"`), and a stack at 999). If the block carries a script, its `on_break(player)` hook runs first, while the cell still has its memory: the hook may `toast`/`log`, move the player, and empty its own store into the player's bag. The reply carries `contents:[{item,qty}]` — everything that landed in the bag besides the usual drop — and `toasts:[…]` from the hook, which the client puts in the same toast as the break. A cell's `block_inventory` rows are handed to the breaker (each stack capped at 999) and deleted with its `block_state` rows and any `block_beams` column it owned, which is broadcast off. A hook that throws is logged, never fatal: the block breaks anyway.)
- `POST /api/world/resync` (session; **403 unless the signed-in username is exactly `admin`**, enforced server-side; the admin settings dialog (**+**) shows the button to the admin only). The repair switch: `world_edits` is the whole truth about the world, so this re-runs it. It deletes every derived row whose cell the edit table no longer holds — stale `world_log` catch-up rows, orphaned `block_state` script memory, orphaned `block_beams` light columns, orphaned `block_inventory` cell stores — then replays all surviving edits (`world_edits`, ≤20,000 rows, chunked) and light columns through the live socket as ordinary `edit`/`beam` frames and broadcasts one `resync` frame. Each client rebuilds its world from the snapshot it just read, which also clears blocks the browser painted that the database never had. Replies `{ok,replayed,truncated,beams,stale:{log,state,beams}}`. Real edits, script memory and light columns survive a resync; the route is idempotent.
- `POST /api/block/interact` `{x, y, z, key?}` (session; **E** in game. No `key` runs the block's `on_interact(player)`, a `key` runs `on_choice(key, player)`. Replies `{ok:true,name,title,menu:[{key,label}],toasts,moved,items}` — the client renders `menu` as the option list — or `{ok:false,reason:"empty"|"unscripted"|"script-error"}`; a broken author script is reported, never a 500. Everything the run can touch is preloaded and flushed around it: the cell's `block_state` rows (a `null` write deletes the row), `block_beams` rewritten from `beam()` and fanned out as a `beam` frame, the cell's `block_inventory` store (a quantity of 0 deletes the row), and the acting player's `inventories` stacks (`give_item`/`take_item` cancel to one upsert per item). `moved`/`items` say the bag or the body changed, so the client re-reads its bag. A `set_player_position` writes `player_state` and pushes a `move` frame to that player's sockets; `set_player_respawn_position` stores the anchor in `player_state.spawn_x/y/z`)
- `POST /api/block/script-check` `{script}` (session; the Studio editor's syntax gate. Runs the draft through the real Lua sandbox with the missing-entry no-op and a tiny instruction/wall budget, so it parses without executing anything meaningful. Replies `{ok:true}` or `{ok:false,error,line}` — the 1-based line the editor marks. Advisory: `POST /api/blocks` still re-checks the script with the normal caps and is the truth.)
- `GET /api/player/state` (session; saved spawn/look, saved `appearance` colours, and `health`) / `POST /api/player/state` (session; persists position, yaw and pitch)
- `GET /api/time` (public; the world's clock as `{phase,epoch,running,set_by,set_at}` — `phase:null` means nobody has dialled it, so every client reads the hour off its own wall clock) / `POST /api/time` (session; **403 unless the signed-in username is exactly `admin`**: `{phase}` dials it, `{running:false}` stops the cycle at the hour it stands, `{running:true}` lets a dialled hour carry on, `{reset:true}` deletes the row and hands the world back to the sun. Every change is pushed to every live socket as a `time` frame and handed to each new socket at `accept`; clients also pull this row at join, on reconnect and when the admin dialog opens)
- `POST /api/player/respawn` (session; health back to 20, position to the saved **spawn anchor** — `player_state.spawn_x/y/z`, which a block script can set with `set_player_respawn_position` — falling back to the surface spawn when no anchor is stored; also tells the live object to clear the dead flag and moves that player's body there for everyone else)
- `POST /api/player/eat` `{item_id}` (session; a `kind='food'` item with `heal > 0`, consumes one from the stack, health capped at 20)
- `POST /api/player/appearance` (session; `{body_colour, head_colour, accent_colour, eye_colour}` as `#rrggbb`, upserted into `player_appearance`)
- `WS /api/world/live` (Durable Object fan-out; sends `{"type":"edit","x","y","z","block_id"}` to every connected client, `{"type":"beam","x","y","z","colour"}` (`colour:null` switches a script-painted light column off) and, after an admin `POST /api/world/resync`, the surviving cells as `edit` frames plus exactly one `{"type":"resync"}` frame — every client that sees it rebuilds its world from the snapshot it re-reads, so the repair reaches everyone, not just the admin who pressed the button — `{"type":"move","name","x","y","z"}` to the player a block script teleported (that client replaces its body and keeps its look; the object has already relocated its cached presence, so the next presence frame confirms the new place instead of dragging them back), presence frames — a client posts `{"type":"pose",name,x,y,z,yaw,pitch,held,appearance,vx,vy,vz}` and the object relays it (pitch/held included) plus a `roster` on `who` and a `leave` on disconnect; appearance and `held` colours are whitelisted to `#rrggbb` server-side — mob frames `{type:"mobs",mobs:[{id,kind,x,y,z,yaw,hostile,hp}]}` ~4 Hz, damage/death frames `{type:"hurt",amount,by,health}`, `{type:"health",health}`, `{type:"died",by}`, `{type:"respawn",health,state}`, body-flash frames `{type:"hit",what:"player"|"mob",id}` (every client flashes that body white for a moment) and `{type:"down",name}` (the dead player's avatar lies down until they respawn). Clients send `{type:"attack",mob_id|target,item_id}` — `mob_id` for a mob, `target` for another player's username, `item_id:""` for bare fists; the object takes the damage from the items row (never the client), rate-limits the swing, and re-checks the distance. A client that missed live frames catches up through `GET /api/world`: `world_log` is a bounded catch-up queue — only the newest 100 edits are kept — and while the socket is down the client refetches the whole voxel window every 4 s, so anything older than the queue comes back in the overlay. Send `{"type":"hello","name",...}` immediately on open — waiting for the first keypress lets a refresh stack ghosts in `presences` until the 25 s heartbeat sweep.)

## Security notes before public launch

- Add email verification, password reset, moderation/reporting, rate limits, audit logs and account deletion.
- Add strict request size limits and stronger abuse controls.
- Do not execute submitted source code on the Worker. This scaffold stores a constrained behaviour JSON description only.
- Never put Cloudflare API tokens in frontend files or Git.
- The frontend and Worker currently use different sites (`github.io` and `workers.dev`). The Worker therefore sets a partitioned cross-site cookie (`SameSite=None; Secure; HttpOnly; Partitioned`) and the frontend uses credentialed CORS. Modern Chromium browsers support this cookie model, but privacy settings or browsers without partitioned-cookie support may block it. A custom frontend domain and Worker API hostname under the same registrable domain is the more portable long-term arrangement.
- CORS currently permits HTTPS GitHub Pages origins and localhost development. Restrict this to your exact GitHub Pages origin once the account/repository URL is settled.
- The 7-day inactivity timer is refreshed by authenticated API requests (throttled to one D1 write per 15 minutes); the 30-day absolute expiry is never extended.
- A public game needs server-authoritative simulation and persistence; this scaffold provides the account/content API plus a small shared-world layer (deterministic terrain, edits-only storage, Durable Object fan-out). Mob simulation and health now live in the `WorldLive` object, but attacks are still *reported* by the client (the object validates the item kind and the distance, not the swing), there are no owned servers or anti-cheat, and client-side chunk streaming around the player is in place.
